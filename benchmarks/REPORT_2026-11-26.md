# Is more checkpointing effort worth it? Profiling report, 2026-11-26

Question after the supervisor meeting: is `unroll` (checkpoint every forecast
step) already the best strategy, or can we get memory that stays flat *and*
runs faster than `unroll`? Data: `benchmarks/data/student_cluster_2026-11-26/`.

Setup: GraphEFM, hierarchical graph, 1° data, bf16, one RTX 5060 Ti (16 GiB),
width 512 (the reference width 1024 does not fit). One update of `off` (1
forecast step) and of `unroll` (2 steps). Shares and ratios should carry over
to other GPUs, absolute numbers will not.

## What we measured

**1. The peak of `unroll` is one step recomputed during backward.**

| Policy | Forward peak | Backward peak |
|---|---|---|
| off, 1 step | 8.7 GiB | 6.2 GiB |
| unroll, 2 steps | 4.2 GiB | 8.7 GiB |

Weights and optimizer take only 0.8 GiB. At the peak 94% of the live memory is
MLP layer outputs (61% ordinary MLP layers, 33% the per-edge MLP in message
passing). About 2.6 GiB of the one-step peak is short-lived temporary buffers,
which checkpointing cannot remove.

**2. What one step stores for backward (5.4 GiB).** Finest mesh level in the
decoder (up and down passes): 36%. Grid-mesh layers: 23%. Encoder and prior
mesh level 0: 12%. Embedders and projections: under 10% together. (The paper
reports grid-mesh edges as dominant at 0.25°; at 1° the mesh processing is
larger.)

**3. No region is cheap to store and slow to recompute.** Every GNN layer costs
about 140 to 165 ms of forward time per GiB it stores. Keeping a part of a step
stored therefore saves time linearly with the memory it costs:

| Extra memory per step | Time vs `unroll` (predicted) |
|---|---|
| 250 MiB | 0.97 |
| 1 GiB | 0.91 |
| 2 GiB | 0.81 |
| 4 GiB | 0.62 |

This is the same straight line as checkpointing fewer steps
(`--ckpt_unroll_steps`). Our pre-agreed bar was at least 15% faster for at most
1 GiB per step; the prediction gives 9%.

**4. Recompute is the forward pass, and it is expensive.** Forward 680 ms,
backward 187 ms, optimizer 14 ms. A full recompute costs 77% of an update, so
`unroll` takes 1.75x (hook-free, 3038 ms for 2 steps vs 867 ms for 1 step; 1.81x
on the A100 at width 1024). The profiler itself adds only about 2%.

**5. The forward pass is bandwidth-bound, not overhead-bound.** At half the
width (256) forward, backward and peak memory all fall to 0.49x. Launch
overhead would not shrink, and matrix multiplies would fall to about 0.25x.
So the time goes into moving data (gather, concatenate, sum over edges,
normalization).

**6. Mixed precision is only a partial leak.** Saved memory is 68% bfloat16 and
32% float32 (1.7 GiB). Making all of it bf16 would save at most about 0.9 GiB
(16% of the saved memory), and only if accuracy allows.

## Conclusion

- **`unroll` is close to the best checkpointing policy for this model.** Its
  memory is flat in the number of steps and its peak is one step's recompute.
  Finer policies (per layer, selective, per region) cannot beat the straight line
  between `unroll` and `off`, because the cost per GiB is the same everywhere.
- **A per-layer or Jane Street style planner is not worth building for the
  single-GPU case** (prediction from one profile; not yet confirmed by a run that
  keeps regions stored).
- **Partial unroll is the practical tool** when memory is spare: with
  `--ckpt_unroll_steps K` and `plan_unroll_steps.py`, each step left stored buys
  time linearly.
- **The remaining potential is in the forward pass itself.** Recompute costs
  77% of an update and is bandwidth-bound, so fusing operations
  (`torch.compile` on the GNN layers, now possible after the graph-break fix),
  avoiding fp32 casts, and not materializing the per-edge concatenation would
  make every policy faster and also lower the peak.
- **A cut at the latent** (two checkpoint blocks per step) should lower the
  peak at unchanged time. Predicted, untested.

## Open and caveats

- Single profile at 1°, width 512, one GPU type. The 0.25° production run may
  have a different split.
- The GPU kernel profile recorded no GPU events on the student cluster. CPU time
  shows 57% in dtype copies (733 conversions); this is unconfirmed and may be
  waiting on the GPU. It could be repeated on Piora.
- Why backward is 3.6x cheaper than forward is still unexplained.
- Not yet tested: keeping regions stored in a real run, `torch.compile` of the
  model, the latent-split block, multi-GPU (recompute vs. halo communication).

## Update 2026-11-27: torch.compile of the GNN layers, and the nested growth

Data: `benchmarks/data/student_cluster_2026-11-27/`. Same GPU and width as above;
`--compile_layers` compiled all 21 GNN layers (`neural_lam/compile_layers.py`).

| | Eager | Compiled | Change |
|---|---|---|---|
| `off`, 1 step: forward | 656 ms | 598 ms | -9% |
| `off`: backward | 183 ms | 176 ms | -4% |
| `off`: peak memory | 8701 MiB | 7968 MiB | -8% |
| `off`: stored after forward | 5.3 GiB | 4.6 GiB | -12% |
| `unroll`, 2 steps: forward | 1315 ms | 1208 ms | -8% |
| `unroll`: backward | 1664 ms | 1524 ms | -8% |
| `unroll`: peak memory | 8709 MiB | 7978 MiB | -8% |

- **Compiling the layers gives a small, free gain** (about 8-9% time and 8-12%
  memory) and the outputs and gradients are unchanged (CPU tests). It does not
  change the picture: the forward pass is still about 76% of an update, so
  `unroll` still costs about 1.75x `off`, and the ranking of policies is the
  same. The forward pass is still about 3.4x slower than backward; the part
  `torch.compile` fuses is evidently not where that time goes.
- **Why `unroll+selective` grows per step (settled on CPU).** Selective
  checkpointing keeps the matrix-multiplication outputs in its own cache, which
  the outer per-step checkpoint does not release before backward. After the
  forward pass `unroll+selective` holds about 8.4 MiB more per step in the CPU
  test, `unroll` and `unroll+internal` about 0.2 MiB. So nesting it under
  `unroll` reintroduces a per-step cost; one more reason to drop it.
- Not yet tested: compile inside a full multi-step training run, whole-model
  compile, partial unroll, and the GPU operation profile (needs Piora; no GPU
  events were recorded on the student cluster).
